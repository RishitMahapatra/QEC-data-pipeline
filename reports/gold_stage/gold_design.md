# Gold design — relational model, ER diagram and requirement coverage

This document brings the whole Gold model together on one page: the ER
diagram, what one row of each table means, the keys and relationships, the
weighted and repeated structures, the rejected relationship, the shared
vocabulary, the design costs, the physical PostgreSQL implementation and the
three SQL analyses. Per-source detail is in
[gold_stage_syndromes.md](gold_stage_syndromes.md),
[gold_stage_google_qec.md](gold_stage_google_qec.md),
[gold_stage_qasmbench.md](gold_stage_qasmbench.md) and
[gold_shared_vocabulary.md](gold_shared_vocabulary.md). The full Part I
report is [part1.md](../part1.md).

All DDL, views and load code are in
[load_postgres.py](../../starter/src/quantum_lake_student/stages/load_postgres.py).
Every table is in the PostgreSQL schema `gold`, and each table carries its
row meaning as a `COMMENT ON TABLE`.

## 3. Row meanings

| Table | One row represents | Grain (key) | Rows |
| --- | --- | --- | ---: |
| `gold_syndrome_experiment` | one simulated physical-fault-rate experiment (one source CSV) | `experiment_id` | 7 |
| `gold_syndrome_pattern` | one distinct 16-bit syndrome pattern (4 rounds × 4 checks), seen in any experiment | `syndrome_bits` | 31,941 |
| `gold_syndrome_observation` | one (experiment, pattern, logical-error label) combination with its physical weight | `observation_id` = (experiment, pattern, label) | 75,598 |
| `gold_google_experiment` | one hardware experiment configuration (basis / distance / rounds / processor location) | `experiment_id` | 5 |
| `gold_google_shot` | one hardware shot in one experiment: its packed bits and actual outcome | `(experiment_id, shot_index)` | 250,000 |
| `gold_google_decoder` | one supplied decoder algorithm | `decoder_name` | 4 |
| `gold_google_decoder_prediction` | one decoder's prediction for one shot, and whether it was wrong | `(experiment_id, shot_index, decoder_name)` | 1,000,000 |
| `gold_qasmbench_circuit` | one parsed circuit variant (source or transpiled) | `circuit_id` | 6 |

## 4. Identifiers and relationships

**Identifier choices.**

- **Natural keys where the source provides one**: `experiment_id` (filename or
  folder name), `circuit_id` (`<benchmark>:<variant>`), `decoder_name`,
  `syndrome_bits` (the pattern is its own identity).
- **Composite keys where identity only holds within a parent**:
  `(experiment_id, shot_index)`, `(circuit_id, register_kind, register_name)`.
- **One hashed surrogate**: `observation_id` is a deterministic hash of
  `(experiment_id, syndrome_bits, logical_error_label)`. The natural 3-column
  key is still enforced as `UNIQUE`. It exists because the ML `example_id`
  needs one stable column.
- **`source_record_id`** (`UNIQUE` on every table that has one) is the
  deterministic Silver row ID, the link in the trace chain
  Gold → Silver → `source_trace` → Bronze.

All identifiers are deterministic (names or hashes of source positions),
never random values or timestamps, so reruns produce the same keys.

**Relationships (all enforced by foreign keys).**

| Parent → child | Cardinality | FK |
| --- | --- | --- |
| `gold_syndrome_experiment` → `gold_syndrome_observation` | 1 : many | `experiment_id` |
| `gold_syndrome_pattern` → `gold_syndrome_observation` | 1 : many (a pattern recurs across experiments and labels) | `syndrome_bits` |
| `gold_google_experiment` → `gold_google_shot` | 1 : 50,000 | `(experiment_id, measurement_count, detector_count)` composite, plus `experiment_id` |
| `gold_google_shot` → `gold_google_decoder_prediction` | 1 : 4 | `(experiment_id, shot_index)` |
| `gold_google_decoder` → `gold_google_decoder_prediction` | 1 : 250,000 | `decoder_name` |
| `gold_qasmbench_circuit` → register / stabilizer_check / conditional_correction | 1 : many (0 checks and corrections for 2 of 3 benchmarks) | `circuit_id`, `ON DELETE CASCADE` |

`gold_syndrome_observation` is the many-to-many bridge between
experiments and patterns, carrying the label and the weight. Likewise,
`gold_google_decoder_prediction` is the bridge between shots and decoders.

## 5. Weighted and repeated structures

| Structure | How Gold stores it | Why |
| --- | --- | --- |
| **Physical weight `quantity`**: one syndrome row stands for up to millions of observations (Σ = 70,000,000 over 7 files; 10,000,000 per file) | kept as `quantity BIGINT CHECK (quantity > 0)` on `gold_syndrome_observation`; **never expanded** into repeated rows | expanding would create ~70M rows instead of 75,598 and add no information. Every aggregate and the ML `sample_weight` use the weight (Q1 sums `quantity`, not rows) |
| **Same syndrome with both labels**: 18,676 patterns occur with label 0 and label 1 in the same experiment | two valid rows, kept apart by `UNIQUE (experiment_id, syndrome_bits, logical_error_label)` | a syndrome alone is not a key. Deduplicating would delete real observations |
| **Patterns repeat across experiments** | 31,941 distinct patterns in `gold_syndrome_pattern`, referenced by 75,598 observations | `triggered_check_count` is computed and stored once per pattern |
| **Repeated predictions per shot**: 4 decoders per shot | 4 rows in `gold_google_decoder_prediction` (1,000,000 rows), not 4 repeated columns | "error rate per decoder" becomes one `GROUP BY`. A fifth decoder needs no schema change |
| **Many detectors per shot**: 200 (d=3) or 600 (d=5) | one packed `BYTEA` per shot (8,750,000 bytes measured), not one row per detector (70,000,000 rows) | the analyses need only `detector_event_count`, and ML needs the packed bytes. See [part1.md §6.5](../part1.md#65-detector-storage-choice-measured) |

## 6. Rejected relationship

**Candidate.** Link the QASMBench circuits `qec_sm_n5` /
`error_correctiond3_n5` to the distance-3 Google experiments and/or the
`d-3` syndrome files, via the shared "distance 3" label (for example an
FK `circuit → google_experiment`, or a join on `distance`).

**Evidence against it, taken from the data:**

| | QASMBench `qec_sm_n5` | QASMBench `error_correctiond3_n5` | Google d=3 | Syndromes d-3 |
| --- | --- | --- | --- | --- |
| Qubits | `q[3]` + `a[2]` = 5 | `q[5]` = 5, no ancilla or syndrome register | 9 data + 8 measure = 17 | not given per row |
| Code | bit-flip **repetition** code (2 parity checks) | no explicit parity-check structure | **surface** code, 200 detectors over 25 rounds | **surface** code, 4 rounds × 4 checks |
| Records | circuit definition, no shots | circuit definition, no shots | 50,000 shots per experiment | aggregate (syndrome, label, quantity) rows |
| Row-level ID shared with other sources | none | none | none | none |

The same distance number refers to different codes with different qubit
counts and different measurement layouts. No row-level identifier links a
circuit statement, a hardware shot and a simulated syndrome.

**Decision.** No foreign key crosses sources (the diagram in §2 has three
disconnected clusters). The rejection is visible in Gold itself:

```sql
SELECT source_name, entity_id, code_family, distance
FROM gold.v_qec_experiment_catalog
WHERE distance = 3;
-- google_qec / qec_syndromes rows: surface_code
-- qasmbench qec_sm_n5 rows:        repetition_code
```

**Cost.** No cross-source question ("does the d=3 circuit predict hardware
error rates?") can be answered by a join. We accept this because any such
join would rest on an invented match.

## 7. Shared vocabulary without invented matches

Every top-level entity carries the same two conformed columns, with the same
type and the same allowed values:

| Column | Constraint | google_qec | qec_syndromes | qasmbench |
| --- | --- | --- | --- | --- |
| `code_family` | `IN ('surface_code','repetition_code')` | `surface_code` | `surface_code` | `repetition_code` for `qec_sm_n5`, else `NULL` |
| `distance` | `> 0` | 3 or 5 | 3 | 3 for `qec_sm_n5`, else `NULL` |

- QASMBench labels are given only where the circuit makes the code explicit.
  `CHECK ((code_family IS NULL) = (distance IS NULL))` makes the pair
  all-or-nothing. The hand-written label is re-checked against the parsed
  stabilizer checks at load time (`_check_repetition_code_labels`): a
  mismatch rolls back the load.
- Other shared ideas use consistent names: `experiment_id`,
  `source_record_id`, `syndrome_bit(s)`. Distinct QEC concepts deliberately
  keep **distinct** names: `detector_bits` (changes between rounds) ≠
  `syndrome_bits` (check outcomes), `actual_observable_flip` ≠
  `predicted_flip` ≠ `was_wrong`.
- `v_qec_experiment_catalog` stacks the sources with `UNION ALL`. It places
  them side by side under one vocabulary and never matches one source's row
  to another's.

Full mapping: [gold_shared_vocabulary.md](gold_shared_vocabulary.md).

## 8. Design choices and their costs

| Decision | Why | Cost |
| --- | --- | --- |
| Syndromes split into **experiment / pattern / observation** instead of copying the flat Silver table | experiment metadata stored once; the pattern becomes an entity; label and weight live in one place | one more join per query |
| **Hashed `observation_id`** PK, natural key kept as `UNIQUE` | ML `example_id` needs one stable column that resolves to exactly one Gold row | not human-readable |
| **Decoder predictions in their own table**, `predicted_flip` and `was_wrong` as separate facts | prediction and mistake are different QEC concepts; per-decoder rates are a single `GROUP BY`; extensible | 1,000,000 rows (larger than the shot table); the ML view must pivot 4 rows back into 4 columns |
| **Copied `measurement_count` / `detector_count` on each shot + composite FK** | a `CHECK` cannot read another table. The copy lets `octet_length(detector_bits) = ceil(detector_count/8)` be checked per row, and the composite FK forces the copy to equal the experiment's value | 8 redundant bytes per shot |
| **Packed `BYTEA` detector bits** | 250,000 rows instead of 70,000,000; byte-for-byte equal to Silver/Bronze | SQL cannot filter on a single detector; unpack in Python (`numpy.unpackbits(..., bitorder="little")`) |
| **QASM register JSON decomposed** into `gold_qasmbench_register` | sizes and kinds become typed, constrained, queryable columns (used by Q3) | one small extra table (16 rows) |
| **`data_qubits` as `TEXT[]`**, not a junction table | ~8 (qubit, check) pairs in the whole archive; order is meaningful | weaker normal form; queried with `= ANY(...)` |
| **No cross-source FKs; shared vocabulary only** | no reliable row-level identifier exists ([§6](#6-rejected-relationship)) | cross-source questions are side-by-side comparisons, not joins |
| **`cardinality(data_qubits) >= 1`** instead of `array_length(...) >= 1` | `array_length('{}',1)` is `NULL`, and a `NULL` CHECK passes, so empty arrays were accepted. A test caught this (`test_stabilizer_check_rejects_empty_data_qubits`) | — |

## 9. Physical implementation in PostgreSQL

### 9.1 Constraints and indexes

| Kind | Implemented |
| --- | --- |
| **Primary keys** | on all 11 tables (§3 grain column) |
| **Alternate keys (`UNIQUE`)** | `(experiment_id, syndrome_bits, logical_error_label)`; `(basis, distance, rounds, center_row, center_col)`; `(experiment_id, measurement_count, detector_count)` (target of the composite FK); `(benchmark_name, variant)`; `(circuit_id, check_id)`; `source_record_id` |
| **Foreign keys** | every child → parent in §4, including the composite shot → experiment FK; QASMBench children use `ON DELETE CASCADE` |
| **Data-driven `CHECK`s** | `0 < physical_fault_rate < 1`; `round_count = 4`, `check_count = 4`; `syndrome_bits` matches `^(0[01]){16}$`; `triggered_check_count BETWEEN 0 AND 16`; `quantity > 0`; `basis IN ('X','Z')`; `(distance=3 AND detector_count=200) OR (distance=5 AND detector_count=600)`; `octet_length(detector_bits) = CEIL(detector_count/8.0)` (same for `measurement_bits`); `detector_event_count <= detector_count`; `variant IN ('source','transpiled')`; `register_kind IN ('qreg','creg')`; `cardinality(data_qubits) >= 1`; `condition_value >= 0`; `code_family`/`distance` both set or both null |

| Index | Serves |
| --- | --- |
| `gold_syndrome_observation(experiment_id)` | Q1 and `v_ml_syndrome_decoder_example` join to experiment |
| `gold_syndrome_observation(syndrome_bits)` | joins to `gold_syndrome_pattern` |
| `gold_google_shot(experiment_id)` | shot → experiment join (Q2, ML view) |
| `gold_google_decoder_prediction(decoder_name)` | Q2 grouping / filtering by decoder |
| `circuit_id` on register, stabilizer_check, conditional_correction | Q3 joins |

Composite PKs already index `(experiment_id, shot_index)` for the
prediction → shot join. Every PK, FK and CHECK has a reject and an accept test
in `starter/tests/test_load_postgres*.py`.

### 9.2 All-or-nothing load

`load_postgres.run()` uses **one transaction for all three sources**:

1. `CREATE SCHEMA IF NOT EXISTS gold`; create tables (`IF NOT EXISTS`).
2. Load Google (truncate + insert), syndromes (upsert on deterministic keys,
   then delete rows no longer in Silver), QASMBench (`TRUNCATE ... CASCADE` +
   insert).
3. Re-count every Gold table with an independent `SELECT COUNT(*)` and
   compare with Silver. A mismatch raises an error.
4. Create the catalog and ML views.
5. `COMMIT` only if every step succeeded. Otherwise `ROLLBACK`, and the
   previous complete Gold state stays untouched.

Upsert guards: a pre-write check raises if two Silver rows map to the same
`observation_id` (silent collision), and stale rows are deleted after the
upsert.

Tests (`starter/tests/test_load_postgres.py`):
`test_run_rolls_back_google_when_syndromes_load_fails`,
`test_run_rolls_back_google_and_syndromes_when_qasmbench_load_fails`,
`test_run_detects_row_count_mismatch_and_rolls_back`. Rerun safety:
`test_rerun_does_not_duplicate_rows`,
`test_row_removed_from_silver_is_removed_from_gold_on_rerun`
(`test_load_postgres_syndromes.py`).

## 11. How to verify

From `starter/` inside the workspace container:

```bash
make run    # Bronze → Silver → Gold → ML → trace; also re-runs the 3 analyses
make test   # includes every Gold PK/FK/CHECK, rollback and rerun test
```

Inspect the implemented schema directly in `psql`:

```sql
-- every table with its row meaning
SELECT c.relname, obj_description(c.oid)
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'gold' AND c.relkind IN ('r', 'v') ORDER BY 1;

-- all PK / UNIQUE / FK / CHECK constraints
SELECT conrelid::regclass AS table_name, contype, pg_get_constraintdef(oid)
FROM pg_constraint WHERE connamespace = 'gold'::regnamespace ORDER BY 1, 2;

-- all indexes
SELECT tablename, indexdef FROM pg_indexes WHERE schemaname = 'gold' ORDER BY 1;
```
